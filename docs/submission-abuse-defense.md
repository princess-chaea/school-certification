# 학생 제출·AI 비용 보호

이 문서는 `codex/submission-abuse-defense-20261011`의 정책과 배포 점검표다. 코드 검증과 운영 배포는 별개이며, 아래 운영 점검은 완료 전까지 미확인으로 남긴다.

## 정상 참여와 제한 기준

첫 자료 수집일에 학생마다 30건 이상을 올릴 수 있어야 한다. 과거에 작성한 기록과 같은 인증 항목의 서로 다른 활동도 받는다. **하루 제출 총량 제한은 없다.** 짧은 시간의 반복 요청과 유료 AI 사용량을 각각 제한한다.

| 대상 | 서버 한도 | 한도에 도달했을 때 |
|---|---|---|
| 학생 증빙 제출 | 학생별 최근 10분 40건, 최근 1시간 120건 | 일시적으로 새 제출을 거절한다. 시간이 지나면 다시 제출할 수 있다. |
| 영어 문장 연습 저장 | 학생별 최근 10분 40회, 최근 1시간 120회 | 새 연습 저장을 잠시 제한한다. 이미 저장된 녹음의 재전송은 같은 기록으로 처리한다. |
| 영어 문장 검사 요청 | 학생별 최근 10분 150회 | 여러 문장을 한 번에 검사 요청할 수 있도록 별도 한도를 둔다. |
| 업로드 이용권 발급 | 학생별 최근 10분 60개, 최근 1시간 150개 | 새 파일 업로드를 잠시 제한한다. 사진·첨부·녹음에 함께 적용한다. |
| 학생 AI 확인 | 학생별 10분 구간 40건, 하루 60건 | 제출 기록은 보존하고 교사 직접 확인으로 넘긴다. |
| 학교 AI 확인 | 하루 최대 3,000건 | 학교 설정값이 더 작으면 그 값을 적용한다. |
| 플랫폼 AI 확인 | 전체 학교 합산 하루 3,000건, 월 50,000건 | 이후 기록은 교사가 직접 확인한다. |

제출·업로드 한도는 이동 시간창, AI 10분 한도는 고정 구간이다. AI 일·월 기준은 서버의 `todayKey()`를 따른다. AI 한도는 요청 건수 상한이며 금액 상한은 아니다. 제공자 지출 한도와 사용량 알림도 별도로 관리한다. 여러 학생이 동시에 30건씩 올리면 학교·플랫폼 한도에 먼저 도달할 수 있다.

## 중복과 조작 처리

- 화면은 전송 중 재클릭을 막고, 서버는 같은 `itemId`의 재시도에 기존 기록을 반환한다. 화면 잠금이 해제되어도 서버 검증은 적용된다.
- 서버가 학생 명단·학교·학년도·학년·인증 항목·과제·증빙 형식을 확인하고 학생 신원, 상태, 인정 횟수를 결정한다. 학생의 Firestore 직접 생성은 최종 규칙에서 차단한다.
- 영어 문장 연습은 서버가 실제 세트·문장·정답과 녹음 이용권을 확인하고 세 번의 연습 및 검사 요청 상태를 결정한다. 학생의 `englishItems` 직접 쓰기도 최종 규칙에서 차단한다.
- 동일 사진은 서버가 읽은 파일 MD5로 학생·학년도·항목·과제 범위에서 중복 처리한다. 업로드 파일명이나 활동일을 바꾸어도 같은 사진은 다시 집계하지 않는다.
- 사진 없는 기록은 항목·과제·활동일·내용·추가 입력값과 첨부/녹음 파일 해시를 비교한다. 공백이나 필드 순서만 바꾼 복제도 기존 기록으로 처리한다. 삭제된 기록은 보완 후 새 기록으로 제출할 수 있다.
- 업로드 이용권은 15분 동안 지정된 한 경로에 파일 하나를 생성하도록 허용한다. 사진은 JPEG 5 MiB, 첨부·녹음은 10 MiB까지이며 덮어쓰기는 금지한다.
- AI 호출 전에 기록별 작업과 모든 사용량을 한 트랜잭션으로 예약한다. 중복 이벤트가 같은 기록에 다시 과금하지 않게 하고 SDK 자동 재시도를 끈다. 한도 초과 사유는 교사용 확인 결과에 남긴다.

동일 파일·내용 검사는 유사 이미지나 의미가 같은 글을 모두 탐지하지 않는다. 이미지를 변형하는 우회와 허용 속도 이하의 장기 악용에는 사용량 관찰과 운영 대응이 필요하다. 업로드 후 제출하지 않은 파일의 정리 정책도 별도로 운영해야 한다.

## 학교 가입 권한

1. 서버가 NEIS 정보로 확인하여 **새 학교를 처음 개설한 가입자는 학교 담당자(관리자)**가 된다. 동시 가입은 트랜잭션으로 처리한다.
2. 기존 학교의 추가 가입자는 기본적으로 즉시 교사로 사용한다. 가입 화면의 관리자 선택만으로 기존 학교의 관리자 권한을 얻을 수 없다.
3. 학교 담당자는 **설정 → 교사·담당자 가입 방식**에서 `가입 즉시 사용`과 `학교 담당자 승인 후 사용`을 바꾸고 저장한다. 추가 관리자 지정은 기존 담당자가 구성원 화면에서 처리한다.
4. 등록된 학생 계정의 교사 가입과 다른 학교에 이미 소속된 계정의 신규 가입은 거절한다. 관리자가 사라진 경우 자동 복구는 최초 학교 개설자에게만 허용한다.

Google 이메일 확인과 NEIS 학교 조회는 실제 교직원 소속을 증명하지 않는다. 기본 즉시 가입과 최초 개설자의 관리자 부여에는 학교 소속을 확인하지 않은 사용자가 접근할 위험이 남는다. 학생 기록을 운영하는 학교는 승인제로 전환하고 가입자를 확인한다.

새 학교는 즉시 개설할 수 있지만 유료 AI는 `aiReviewEnabled: false`로 시작한다. 플랫폼 운영자가 사용을 허용하기 전에도 기록 제출과 교사 확인은 가능하다. 학교 담당자는 클라이언트에서 이 서버 전용 설정을 바꿀 수 없다.

## 비밀키와 App Check

`ANTHROPIC_API_KEY`는 Cloud Functions의 Secret Manager 바인딩으로만 읽는다. 프런트엔드 환경 변수·번들·응답·로그에 키를 넣지 않는다. 키가 노출되었다는 증거가 있으면 해당 키를 폐기하고 교체한다.

App Check는 후속 배포 항목이다. 먼저 reCAPTCHA Enterprise 제공자와 운영 도메인을 등록하고 웹앱에서 토큰을 발급받도록 한 뒤, 실제 학생·교사 브라우저와 설치형 PWA의 유효 요청 비율을 확인한다. 정상 토큰 발급을 확인한 후 Callable의 `enforceAppCheck`와 Firestore·Storage 적용을 단계적으로 켠다. 현재 브랜치의 Callable에는 강제가 켜져 있지 않다. [웹 제공자 설정](https://firebase.google.com/docs/app-check/web/recaptcha-enterprise-provider), [Callable 적용](https://firebase.google.com/docs/app-check/cloud-functions).

App Check를 켜더라도 로그인·학교 권한·중복 검사·요청 한도를 유지한다. 유효한 앱과 계정에서도 반복 요청을 만들 수 있다.

## 운영 배포 순서

이 변경은 Vercel 화면만 배포해서 완료되지 않는다. Firebase Functions와 Firestore·Storage 규칙을 함께 전환한다.

1. **사전 검증:** 아래 로컬 검사와 에뮬레이터 점검을 완료한다. 배포할 커밋, 기존 규칙 및 함수 버전, 운영 프로젝트를 기록한다. 기존 학생 기록을 삭제하거나 초기화하지 않는다.
2. **전환 구간 보호:** `firebase.transition.json`에 지정된 `deploy/firestore.transition.rules`를 먼저 적용한다. 이 규칙은 기존 학생 제출은 계속 받되 클라이언트의 `serverValidated` 필드 작성을 차단한다. 구형 규칙을 그대로 둔 상태에서 새 AI 함수를 배포하면 이 필드를 위조해 유료 AI 확인을 호출할 수 있다. 전환 규칙은 최종 방어가 아니며, 학생의 직접 문장 기록과 제출은 최종 규칙 적용 전까지 남는다.
3. **Functions:** `submitEvidence`, `issueUploadTicket`, `saveSentencePractice`, AI 트리거, 가입 관련 함수와 공통 설정 변경을 먼저 배포한다. 운영 함수 준비 상태를 확인한다.
4. **프런트엔드:** 이용권 발급 → 파일 업로드 → Callable 제출 흐름을 배포한다. 곧바로 최종 규칙 단계로 이어간다. 구 Storage 규칙은 새 PDF/HWP 첨부를 허용하지 않으므로 이 중간 상태에서 첨부 성공을 점검 기준으로 삼지 않는다.
5. **최종 규칙과 기능 확인:** 학생의 Firestore 직접 제출을 닫고 Storage 이용권을 필수로 한다. 그 후 새 화면에서 사진·첨부·녹음·문장 연습의 정상 업로드와 콘솔의 직접 쓰기 거절을 함께 확인한다. 이 단계가 끝나야 서버 제한 우회 경로가 닫힌다.
6. **구형 PWA와 실제 계정:** 오래 열어 둔 탭과 설치형 PWA는 이전 코드를 계속 실행할 수 있다. 최종 규칙 후 구형 업로드·제출은 실패하므로 갱신 안내, 재접속, 입력 보존과 재제출을 실제 기기에서 확인한다.
7. **운영 관찰:** 제출 거절률, 업로드 이용권 발급률, AI 한도별 건너뜀, 함수 오류, AI 제공자 사용량을 확인한다. 차단이 정상 참여에 영향을 주면 수치를 조정하되 학생 기록과 서버 검증 경로를 유지한다.

전환 규칙만 배포하는 명령은 `firebase deploy --config firebase.transition.json --only firestore:rules --project school-certification-e1a6c`이다. 운영 프로젝트와 기존 규칙 백업을 확인한 뒤 실행한다. 최종 규칙은 기본 `firebase.json`의 `firestore.rules`를 사용한다. 이 브랜치에서는 두 규칙 모두 운영에 배포하지 않았다.

장애 시 새 Callable을 사용하는 정상 버전으로 복구하거나 일시 점검을 안내한다. 학생 직접 쓰기를 다시 열면 중복·속도 제한을 우회할 수 있으므로 규칙만 이전 버전으로 되돌리는 것을 기본 복구 방법으로 삼지 않는다.

## 검증 명령과 남은 점검

저장소 루트에서 다음 명령을 실행한다. Node.js와 설치된 루트·Functions 의존성이 필요하다. Functions 테스트는 컴파일 후 실행한다.

```powershell
npm run typecheck
npm test
npm --prefix functions run build
node --test functions/lib/submitEvidence.test.js functions/lib/uploadTicket.test.js functions/lib/saveSentencePractice.test.js functions/lib/tenancy.test.js
npm run build
git diff --check
```

2026-10-11 로컬 확인: 타입 검사, 공유 테스트 28개, Functions 빌드, 제출·업로드·문장·가입 단위 테스트 31개, 웹/PWA 빌드가 통과했다. 웹 빌드에는 500 kB 초과 번들 경고가 있다. 이 결과는 운영 권한·Firestore 트랜잭션 경합·Storage 규칙 통과를 증명하지 않는다. 이후 코드가 바뀌면 관련 검사를 다시 실행한다.

- [ ] 에뮬레이터: 학생의 직접 생성·다른 학생 파일 참조·이용권 없는 업로드·만료/재사용/덮어쓰기를 거절한다.
- [ ] 에뮬레이터: 병렬 재전송·동일 사진·동일 내용이 한 건만 저장되고 집계된다. 삭제 후 보완 제출도 확인한다.
- [ ] 에뮬레이터: 정상 30건을 받고 41번째/121번째 급속 제출과 61번째/151번째 이용권 발급을 제한하며 시간창 만료 후 복구한다.
- [ ] 에뮬레이터: AI 각 한도와 중복 트리거에서 추가 유료 호출이 발생하지 않고 교사 확인할 기록이 남는다.
- [ ] 에뮬레이터: 최초 동시 가입의 관리자 한 명, 후속 교사의 즉시/승인 가입, 관리자 자가 승격 거절을 확인한다.
- [ ] 에뮬레이터: 영어 문장 직접 쓰기 거절, 정상 3회 연습·대량 검사 요청·재시도·교사 반려 후 추가 연습을 확인한다.
- [ ] 실제 학생·교사 계정: 모바일·설치형 PWA·새로고침·통신 재시도·영어 문장 녹음·교사 최종 승인과 진행도를 확인한다.
- [ ] 운영 배포 커밋, Firebase 규칙/함수 버전, Vercel 배포 및 실제 계정 확인 결과를 기록한다.
